# Skill: build-workflow-packaging

## Purpose

The Docker image is the formal boundary between the product-workflow and the
Dark Factory. Everything the Dark Factory needs at runtime must be inside the
image or injected via environment variables at run time. This skill defines
exactly what goes in, how to assemble it, and how to verify the assembly is
complete before the image is handed over.

---

## Image Workspace Layout

The container's working directory is `/workspace`. The Dark Factory runs
`claude` inside the container pointed at `/workspace`.

```
/workspace/
├── CLAUDE.md                     # Dark Factory config (from project)
├── commands-map.yaml             # Populated by package agent
├── docs/
│   ├── features/                 # BDD .feature files
│   ├── specs/                    # Specification documents
│   │   └── api/                  # OpenAPI / AsyncAPI contracts
│   ├── architecture/
│   │   ├── system.md
│   │   └── adrs/
│   ├── designs/                  # Design artefacts (if project has UI)
│   └── build/
│       ├── dev-log.md            # Initialised with header; Dark Factory appends
│       └── sufficiency-report.md # Carried in for Dark Factory reference
├── standards/                    # Vendored snapshot of shared standards
└── .claude/                      # Dark Factory workflow (build-workflow baseline)
    ├── agents/
    ├── skills/
    ├── hooks/
    └── settings.json
```

**State at runtime:** The container runs with a git repository mounted at
`/workspace` (or a project subdirectory). Generated code, test results, and
dev-log entries accumulate in the mounted repo. The image provides the template;
the mount provides persistence.

**Entrypoint behaviour:** On container start, the entrypoint script:
1. Copies the baked-in workspace template from `/workspace-template/` to
   `/workspace/` if `/workspace/CLAUDE.md` does not already exist (idempotent
   initialisation for the mounted repo).
2. Invokes Claude Code in autonomous mode pointed at `/workspace`.

## commands-map.yaml Schema

The `commands-map.yaml` file maps abstract command keys to concrete shell
commands for the project's declared stack. The Dark Factory runs these
commands via the keys — it never constructs commands directly.

### Required Keys

| Key | Purpose |
|-----|---------|
| `format` | Auto-format source code in place |
| `lint` | Run linter; exit non-zero on violations |
| `typecheck` | Run type checker; exit non-zero on errors |
| `test_unit` | Run unit test suite |
| `test_integration` | Run integration test suite |
| `coverage` | Run tests with coverage; output coverage report |
| `build` | Compile / bundle the project |
| `app_run` | Start the application (used for E2E and smoke tests) |

### Verify-Alignment Keys

| Key | Purpose |
|-----|---------|
| `verify_architecture` | Run the build's own architectural fitness functions (its guardrail), derived from the project's architecture-rules manifest; hard-gates each slice. |
| `mutation` | Run the mutation engine over a target set — used to prove a guardrail check has teeth by killing a known-violating mutant. |

Required whenever an architecture-rules manifest is present (i.e. always, post-design).

### Conditional Keys

| Key | When required |
|-----|---------------|
| `test_e2e` | Slice plan lists E2E tests, or entry point is UI/API with external consumers |
| `security_scan` | Any slice touching trust boundaries, auth, or external integrations |
| `dependency_scan` | Any slice introducing new dependencies |
| `secrets_scan` | Any slice handling credentials, tokens, or PII |
| `deploy_dev` | When development deployment target is declared |
| `deploy_staging` | When staging deployment target is declared |
| `deploy_prod` | When production deployment target is declared |

### Format

```yaml
# commands-map.yaml
# Generated by product-workflow package agent.
# All commands run from the project root. Non-interactive. Fail loudly.

format:        "npx prettier --write ."
lint:          "npx eslint . --max-warnings 0"
typecheck:     "npx tsc --noEmit"
test_unit:     "npx jest --testPathPattern=unit"
test_integration: "npx jest --testPathPattern=integration"
test_e2e:      "npx playwright test"
coverage:      "npx jest --coverage --coverageThreshold='{\"global\":{\"lines\":95}}'"
build:         "npm run build"
app_run:       "node src/index.js"
verify_architecture: "# stack fitness runner, e.g. npx tsx tools/fitness/run.ts"
mutation:      "# stack mutation engine, e.g. npx stryker run"
security_scan: "npx semgrep --config=auto src/"
dependency_scan: "npm audit --audit-level=high"
secrets_scan:  "npx gitleaks detect --source . --no-git"
deploy_dev:    "# TODO: configure dev deployment target"
deploy_staging: "# TODO: configure staging deployment target"
deploy_prod:   "# TODO: configure production deployment target"
```

**Rules:**
- All commands run from the project root (not from subdirectories)
- All commands are non-interactive (no prompts, no TTY requirements)
- All commands exit non-zero on failure — never suppress errors
- Commands must not modify source code as a side effect (except `format`)
- `build` must emit a single, content-addressed artefact (record its hash); those
  same bytes are what `verify` certifies and what deployment promotes — never a
  rebuild between passing and shipping
- `# TODO:` placeholders are permitted for deploy keys when no target is
  declared; all other keys must have a concrete command

## Stack Inference Rules

### Node.js (Express / Fastify / plain Node)

Indicators: `package.json` in project root, `node` or `express` in ADRs/Section 3.

| Key | Default command | Notes |
|-----|-----------------|-------|
| `format` | `npx prettier --write .` | Add `.prettierrc` if not present |
| `lint` | `npx eslint . --max-warnings 0` | ESLint with zero tolerance |
| `typecheck` | `npx tsc --noEmit` | Only if TypeScript declared; else `echo 'no typecheck'` |
| `test_unit` | `npx jest --testPathPattern=unit` | Vitest: `npx vitest run unit` |
| `test_integration` | `npx jest --testPathPattern=integration` | |
| `test_e2e` | `npx playwright test` | Cypress: `npx cypress run` |
| `coverage` | `npx jest --coverage` | Vitest: `npx vitest run --coverage` |
| `build` | `npm run build` | If no build step: `echo 'no build step required'` |
| `app_run` | `node src/index.js` | Check `package.json` main field |
| `security_scan` | `npx semgrep --config=auto src/` | |
| `dependency_scan` | `npm audit --audit-level=high` | |
| `secrets_scan` | `npx gitleaks detect --source . --no-git` | |

**Ambiguous cases — escalate rather than guess:**
- Multiple test runners present (Jest + Vitest): ask which is primary
- Non-standard entry point: ask for the start command
- Monorepo structure: ask which package is the application root

### Escalation Triggers

Always escalate to the Product Engineer (do not default silently) when:

- The tech stack section declares a language but not a test framework, and
  multiple plausible frameworks exist for that language
- The project has a non-standard directory structure (not `src/`, not root-level)
- The deployment infrastructure is not declared in ADRs or Section 3
- The project uses a polyglot stack (e.g., Go backend + TypeScript frontend)
  — confirm which commands-map keys apply to which component

## Self-Contained Build Context Assembly

**This is mandatory and runs before the Dockerfile is written.** The default
handoff model is **Option A — git-committable source context**: the assembled
context directory is committed to a git repository and `docker build`-able
standalone on any host, with no dependency on the surrounding product-workflow
checkout. For this to hold, the build context must physically contain
everything the Dockerfile `COPY`s — it is not enough for those paths to exist
elsewhere in the product-workflow tree.

The package agent assembles the context at `projects/{name}/` (the build
context) so that a fresh clone of that directory builds the image with no
external inputs:

| What | Source | Destination in build context |
|------|--------|------------------------------|
| Spec artefacts | `projects/{name}/docs/` | already in place |
| Project config | `projects/{name}/CLAUDE.md`, `commands-map.yaml` | already in place |
| Standards snapshot | product-workflow root `standards/` | **copied to** `projects/{name}/standards/` |
| Dark Factory workflow | the **build-workflow baseline** `.claude/` | **vendored to** `projects/{name}/.claude/` |
| Dockerfile + entrypoint | generated | `projects/{name}/Dockerfile`, `docker-entrypoint.sh` |

**Build-workflow baseline path:** the location of the build-workflow `.claude/`
baseline is **not hardcoded in this skill**. The package agent MUST confirm it
with the Product Engineer before vendoring (it is a per-installation path).
**Escalate, do not guess** — vendoring a wrong or locally-modified
build-workflow defeats the purpose of the handoff. Record the resolved
baseline path and its source commit/version in `package-report.md` for
provenance.

**Reproducibility (the Option A trade-off mitigation):** Option A rebuilds the
image from the Dockerfile, so a naive template would drift between the
validated build and a later rebuild. Two pins close this:

1. **Base image pinned by digest.** The package agent resolves the digest of
   the base image at package time (`docker buildx imagetools inspect` or from
   the pulled image's `RepoDigests`) and writes the `@sha256:...` form into
   the Dockerfile. A floating `node:20-slim` tag is NOT acceptable in the
   emitted Dockerfile.
2. **Claude Code pinned to an exact version.** The package agent resolves the
   current stable `@anthropic-ai/claude-code` version at package time and
   writes the exact version into the Dockerfile. A floating install is NOT
   acceptable in the emitted Dockerfile.

Both resolved values are recorded in `package-report.md`. The spec artefacts
are already deterministic (copied verbatim); these two pins make the toolchain
deterministic too, giving Option A most of a registry image's reproducibility
without the registry credential or opacity.

**Phase-2 additive path (not default):** pushing the built image to a private
registry (e.g. GitHub Container Registry) is an *additive* `docker push` step,
not a replacement. It does not require changing the context-assembly or pin
logic. Document it; do not implement it unless the Product Engineer requests
off-host or registry distribution.

## Dockerfile Template

```dockerfile
# syntax=docker/dockerfile:1
# Dark Factory handoff image for {project-name}
# Generated by product-workflow package agent — {date}
#
# Reproducible-rebuild (Option A) handoff: base image and Claude Code are
# pinned. This Dockerfile + its build context (this directory) are committed
# to git and rebuild byte-stably on any host with Docker.

# Base image pinned by digest — resolved by the package agent at package time.
# {NODE_DIGEST} is the sha256 of node:{NODE_VERSION}-slim at package time.
ARG NODE_VERSION=20
FROM node:{NODE_VERSION}-slim@{NODE_DIGEST} AS base

# ── System dependencies ───────────────────────────────────────────────────────
RUN apt-get update && apt-get install -y --no-install-recommends \
    git \
    curl \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# ── Claude Code ───────────────────────────────────────────────────────────────
# Pinned to an exact version — resolved by the package agent at package time.
ARG CLAUDE_CODE_VERSION={CLAUDE_CODE_VERSION}
RUN npm install -g @anthropic-ai/claude-code@${CLAUDE_CODE_VERSION}

# ── Workspace template assembly ───────────────────────────────────────────────
# The workspace template is baked into the image.
# At runtime, the entrypoint copies it into /workspace if not already present
# (enabling idempotent initialisation when a git repo is mounted).

WORKDIR /workspace-template

# Spec artefacts
COPY docs/ ./docs/

# Project configuration
COPY CLAUDE.md ./
COPY commands-map.yaml ./

# Initialise dev-log with header row (Dark Factory appends to this)
RUN mkdir -p docs/build && \
    echo "| Date | Phase | Agent | Description | Outcome |" > docs/build/dev-log.md && \
    echo "|------|-------|-------|-------------|---------|" >> docs/build/dev-log.md

# Standards (vendored snapshot)
COPY standards/ ./standards/

# Dark Factory workflow (build-workflow baseline)
COPY .claude/ ./.claude/

# ── Project runtime tooling ───────────────────────────────────────────────────
# Install the project's declared stack so the Dark Factory can run tests and builds.
# This section is customised per-project by the package agent based on CLAUDE.md Section 3.

# [CUSTOMISE: replace with project-specific tooling installation]
# Example for Node.js projects:
# COPY package.json package-lock.json ./
# RUN npm ci --omit=dev

# ── Entrypoint ────────────────────────────────────────────────────────────────
COPY docker-entrypoint.sh /usr/local/bin/docker-entrypoint.sh
RUN chmod +x /usr/local/bin/docker-entrypoint.sh

WORKDIR /workspace
ENTRYPOINT ["/usr/local/bin/docker-entrypoint.sh"]
```

**Customisation points** (package agent fills in per-project):
- `ARG NODE_VERSION` — matches the declared runtime version
- `FROM` base image — `node:N-slim`, `python:N-slim`, `golang:N`, etc.
- Runtime tooling section — `npm ci`, `pip install`, `go mod download`
- Any additional system packages required by the test suite

## Entrypoint Script Template

```bash
#!/usr/bin/env bash
# docker-entrypoint.sh — Dark Factory container entrypoint
# Initialises the workspace and invokes Claude Code in autonomous mode.

set -euo pipefail

# ── Workspace initialisation ──────────────────────────────────────────────────
# If /workspace/CLAUDE.md does not exist, this is a fresh mount.
# Copy the baked-in template so the Dark Factory has its configuration.
if [ ! -f /workspace/CLAUDE.md ]; then
    echo "Initialising workspace from template..."
    cp -r /workspace-template/. /workspace/
    echo "Workspace initialised."
else
    echo "Workspace already initialised. Resuming from current state."
fi

# ── Validate workspace ────────────────────────────────────────────────────────
required_files=(
    "/workspace/CLAUDE.md"
    "/workspace/commands-map.yaml"
    "/workspace/.claude/agents/navigator.md"
    "/workspace/docs/build/dev-log.md"
)

for f in "${required_files[@]}"; do
    if [ ! -f "$f" ]; then
        echo "ERROR: Required file missing from workspace: $f" >&2
        echo "The handoff image may be incomplete. Aborting." >&2
        exit 1
    fi
done

# ── Invoke the Dark Factory ───────────────────────────────────────────────────
echo "Starting Dark Factory..."
echo "Project: $(grep '^# ' /workspace/CLAUDE.md | head -1 | sed 's/# //')"
echo "---"

exec claude \
    --dangerously-skip-permissions \
    --print \
    "invoke the navigator agent to begin the build"
```

**Notes:**
- `--dangerously-skip-permissions` enables autonomous mode (no interactive
  approval prompts). This is intentional and safe inside a purpose-built container.
- `--print` runs non-interactively and outputs to stdout.
- The initial prompt instructs Claude Code to invoke the navigator agent,
  which reads the dev-log and begins routing through the build slices.
- The `exec` replaces the shell process with Claude Code (clean signal handling).

## Image Validation Checklist

Run these checks after `docker build` and before tagging.
All checks must pass. Fix and rebuild if any fail.

```bash
IMAGE={project-name}:latest

# 1. Workspace structure
docker run --rm $IMAGE ls \
    /workspace-template/CLAUDE.md \
    /workspace-template/commands-map.yaml \
    /workspace-template/docs/features/ \
    /workspace-template/docs/build/dev-log.md \
    /workspace-template/standards/ \
    /workspace-template/.claude/agents/navigator.md
# Expected: all paths exist (exit 0)

# 2. Claude Code availability
docker run --rm $IMAGE claude --version
# Expected: version string printed (exit 0)

# 3. commands-map.yaml has no empty required values
docker run --rm $IMAGE python3 -c "
import yaml, sys
with open('/workspace-template/commands-map.yaml') as f:
    data = yaml.safe_load(f)
required = ['format','lint','test_unit','test_integration','coverage','app_run']
missing = [k for k in required if not data.get(k) or data[k].startswith('# TODO')]
if missing:
    print('Missing or TODO required keys:', missing)
    sys.exit(1)
print('commands-map.yaml: OK')
"

# 4. Standards present
docker run --rm $IMAGE ls /workspace-template/standards/
# Expected: standard files listed (bdd.md, etc.)

# 5. Dark Factory agents present
docker run --rm $IMAGE ls /workspace-template/.claude/agents/
# Expected: navigator.md, plan.md, slice-cycle.md, evolve.md, etc.

# 6. Entrypoint is executable
docker run --rm --entrypoint /bin/sh $IMAGE -c \
    "test -x /usr/local/bin/docker-entrypoint.sh && echo 'Entrypoint: OK'"
```

## Dark Factory Verify-Alignment Obligations

The handoff must let the Dark Factory operate under the verify model (root `CLAUDE.md`
Rules 7-8). The package agent vendors the artefacts and commands that make this possible;
the build-workflow baseline itself must already implement the behaviour.

Vendored into the image (so the Dark Factory can build its own guardrails):
- the architecture-rules manifest `docs/architecture/fitness.md` (and the data-model /
  NFR clause sets) — read-only to the build;
- `commands-map.yaml` with `verify_architecture` and `mutation` populated.

Excluded from the image:
- `projects/{name}/verification/` — verify authors its own suite independently; the Dark
  Factory neither ships nor edits it.

The Dark Factory (build-workflow) must, per the vendored baseline:
- build its **own** architectural fitness functions from the manifest and hard-gate each
  slice on them, held to verify's standard (traced to clauses, proven to have teeth via
  `mutation`);
- treat the manifest and all spec artefacts as **read-only** — a disputed rule escalates
  to product-workflow `design` -> `sufficiency-check`, never edited; fix code, never a
  test, to pass;
- emit a single **content-addressed** artefact so verify can certify the exact bytes that
  ship;
- record the **manifest version** it built against in a form the neutral harness stamps
  (never a plain self-report), for verify's provenance check.

> Cross-repo note: the build-workflow (Dark Factory) agents and skills live in their own
> repository and are only *vendored* here as a baseline. The behaviours above must be
> implemented in that repository's baseline; this skill and the package agent only ensure
> the handoff carries the manifest, the commands, and the exclusions. Vendoring a baseline
> that does not implement Rules 7-8 yields a non-conformant handoff.

```
{project-name}:{YYYY-MM-DD}         # Date-based release tag
{project-name}:latest               # Always points to most recent build
```

`{project-name}:{YYYY-MM-DD}-{N}`

Record the full image name and tag in `docs/build/package-report.md` for

## Handoff Model — Option A: Git-Committable Source Context (default)

The default handoff is **not** a local-daemon-only image. The artefact that
is handed off is the **assembled build context directory** itself —
`projects/{name}/` containing the pinned `Dockerfile`, `docker-entrypoint.sh`,
`commands-map.yaml`, `CLAUDE.md`, `docs/`, the vendored `standards/`, and the
vendored build-workflow `.claude/`.

Handoff steps (the package agent documents these in `package-report.md` and
the final summary; the **Product Engineer performs the git operations** — no
product-workflow agent has git permissions, by design):

1. The package agent assembles the self-contained context and builds + validates
   the image locally (proving the context builds cleanly).
2. The Product Engineer initialises/commits the context directory to a git
   repository and pushes it.
3. Any host that needs to run the Dark Factory clones the repo and rebuilds:
   `docker build -t {project-name}:{tag} .` — the pins guarantee the rebuild
   matches the validated image.

**Why this is the default:** smallest footprint (text + small vendored trees,
no multi-hundred-MB image blob in git), fully diffable handoff, zero registry
credentials, reproducible via the digest + version pins. Consistent with the
product-workflow's deliberate "agents do not touch git; the Product Engineer
owns the repo" boundary.

**Registry distribution (Option B) is phase-2 and additive:** if the Dark
Factory must run on hosts without a build toolchain, or a hard immutability
guarantee is required, add a `docker push` to a *private* registry after
validation. This is documented, not implemented, unless requested.

## Running the Dark Factory

Each handoff includes a ready-to-run launcher, `run-dark-factory.sh`, which the `package`
agent emits into `projects/{name}/` from this skill's
`assets/run-dark-factory.sh.template`. Prefer the launcher over a bare `docker run`: it
mounts the project's git repo, builds the image if missing, and — critically — resolves
Claude Code authentication inside the container. The raw command is the fallback.

### Authentication (what a bare `docker run` gets wrong)

Claude Code inside the container needs credentials. The launcher resolves them in priority
order; this logic is preserved **verbatim** in the template because it is fiddly and easy
to reintroduce bugs into (do not paraphrase or re-derive it):

1. `CLAUDE_CODE_OAUTH_TOKEN` — Claude Max/Pro plan OAuth token (no extra billing). Set
   once on the host with `claude setup-token`, then `export CLAUDE_CODE_OAUTH_TOKEN=<token>`.
2. **macOS Keychain** — if no env token, the launcher transparently extracts the access
   token from the `Claude Code-credentials` Keychain entry.
3. `ANTHROPIC_API_KEY` — fallback; separate Anthropic API billing.

OAuth tokens can expire mid-build; the launcher detects a "Not logged in" failure and
prints refresh instructions.

**Do NOT mount the host `~/.claude/` into the container.** The host `settings.json`
registers hooks pointing at host paths that do not exist in the container, which breaks the
run. Mount only the workspace.

### Emit and run

The `package` agent substitutes the template placeholders — `{{PROJECT_NAME}}`,
`{{IMAGE_TAG}}` (`{project-name}:{tag}`), `{{DEFAULT_WORKSPACE}}` (the project's git repo
path), `{{REPO_URL}}` (the project remote, or empty) — and writes
`projects/{name}/run-dark-factory.sh` (chmod +x). Then:

```bash
cd projects/{name}
./run-dark-factory.sh [workspace-path]   # workspace-path optional; defaults to {{DEFAULT_WORKSPACE}}
```

### Raw fallback

```bash
docker run --rm \
    -v /path/to/project-git-repo:/workspace \
    -e CLAUDE_CODE_OAUTH_TOKEN="$CLAUDE_CODE_OAUTH_TOKEN" \
    {project-name}:{tag}
# ...or -e ANTHROPIC_API_KEY="$ANTHROPIC_API_KEY" in place of the OAuth token
```

**Optional at runtime:**
- `-e ANTHROPIC_MODEL=...` — override the default model
- `--memory=8g` — container memory limit for large projects
- `-e DARK_FACTORY_ESCALATION_WEBHOOK=https://...` — escalation channel (leave unset for
  MVP-1)
